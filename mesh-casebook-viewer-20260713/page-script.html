MESH System Concept

Purpose: Explain MESH as one ecosystem connecting sensing, control, integration, and operation.

This page explains the basic concept of MESH. We divide the system into four roles: sense, control, integrate, and operate.

The important point is that MESH does not have to start as a full automation system. Depending on the farm’s current decision, it can start as a monitoring layer, a control base, a retrofit interface, or a phased automation platform.

This modular structure is useful because every greenhouse has a different starting point: some farms need sensors first, some need control, and some already have controllers but need better data visibility.

MESH Product Lineup

Purpose: Describe each product by role, not by catalog-style selling.

Here we show the product family. AI Hub is the local orchestration and data continuity layer. Control Box and FR/SW modules handle field control. Air Nano provides internal climate sensing. MESH Link is used for validated third-party integration.

The selection logic is practical: we do not install everything from the beginning. We select the minimum useful combination based on the site objective, device schedule, interface map, and operating logic.

For research collaboration, the interesting part may be how these modules can create structured datasets from real greenhouse operations.

App / Web Workflow

Purpose: Show that hardware becomes useful only when operators can act on the data.

This page shows the MESH App and Web workflow. For growers, the value is not only collecting data. They need to see current conditions, understand trends, keep operation records, and respond faster.

The current core is status, alerts, trends, history, logs, and remote visibility. Advanced analysis and AI guidance can be added after the data structure and site behavior are validated.

Page 5

Third-party Endpoints

Purpose: Explain integration carefully: possible, but only after validation.

MESH can connect third-party endpoints such as weather stations, root-zone sensors, nutrient solution systems, and existing controllers through MESH Link.

However, we are careful about integration. An RS-485 port alone does not confirm compatibility. We need the exact model, firmware, physical interface, protocol, register map, access rights, power, and wiring conditions.

So our approach is read-first and validation-first. We start by making data visible, then consider deeper integration only when the interface and safety boundaries are clear.

1 ha Greenhouse Reference

Purpose: Show that MESH can scale into section-level greenhouse operation.

This is a 1 hectare greenhouse reference. The point is that a large greenhouse should not always be treated as one climate point. MESH can group the greenhouse into sections and sensor groups.

Local sensor data can support section-level logic, while the Hub and App/Web provide visibility across the whole site.

The final design still depends on the actual layout, communication conditions, product revision, and sensor measurement scope.

Case 01 · Venlo Strawberry Greenhouse

Purpose: Explain section-level control for a new-build commercial greenhouse.

This case is a 3,500 square meter Venlo glass strawberry greenhouse in France. The greenhouse has nine structural spans, but the practical operating logic is three sections.

This distinction is important. We try to design around real operating sections, not just physical structure. That means manifold groups, valves, screens, vents, and the tenant operation model should define the control logic.

The reusable takeaway is simple: use the greenhouse structure as a starting point, but define the real operating sections from how the grower will actually operate the farm.

Page 9

Case 02 · Blueberry Pilot to 1 ha Expansion

Purpose: Show phased adoption from pilot to larger greenhouse operation.

This case considers a substrate blueberry project in Georgia, starting from a 0.2 to 0.3 hectare pilot and expanding toward a 1 hectare reference system.

The key idea is that Phase 1 should be a real operating pilot, not just a small sensor demo. It should validate climate, root-zone conditions, weather context, and basic operation logic.

Then, when the project expands, the Hub, panel, sensors, weather assets, and data structure can remain useful instead of being rebuilt from the beginning.

Page 10

Case 03 · Egypt Lean Base

Purpose: Explain how to propose MESH when crop and operation details are still open.

This case is a 4,500 square meter greenhouse in Egypt. The crop, cultivation method, irrigation strategy, and actuator schedule were not fully confirmed at the beginning.

In this situation, we avoid over-designing. We propose a lean base: Hub, Control Box, provisional control channels, internal air sensors, and optional weather context.

The reusable takeaway is that when site details are open, a lean base plus selectable options keeps the discussion practical and flexible.

Page 11

Case 04 · Open-field Monitoring

Purpose: Show that MESH can also work as a distributed data layer beyond greenhouses.

This case is a 4 hectare open-field monitoring reference. The starting scope connects soil moisture, temperature, EC points, and weather data into one MESH workflow.

For open fields, the biggest questions are not only sensors. We also need to validate power, communication, outdoor protection, irrigation zones, and whether the data density is representative enough.

The reusable takeaway is that MESH can start as a field data baseline before the permanent sensor density, RF design, and power design are fixed.

Page 12

Case 05 · Retrofit / Read-first

Purpose: Explain the safest way to modernize existing greenhouses.

This case is an existing 1,280 square meter rooting greenhouse with third-party climate, irrigation, fogging, and heating controllers already in place.

Our recommendation is to start with independent crop-level climate monitoring first. Then, in Phase 2, we review read-only controller data through MESH Link only if manuals, ports, protocol, and register maps are validated.

This is important because retrofit projects should not disturb existing safety and local control logic too early. MESH can add visibility, history, and integration readiness while existing controllers keep their authority.

Page 13

What the Cases Show

Purpose: Summarize the common strategic pattern across all cases.

Across the five cases, the strongest message is not one fixed package. The message is that MESH adapts to the starting point of the farm.

For a new-build greenhouse, we can start from section-level control. For a phased project, we validate Phase 1 and expand. For uncertain sites, we use a lean base. For open fields, we start with a representative data baseline. For retrofit sites, we use monitoring-first and read-first integration.

This pattern is useful for collaboration discussions because we can first identify the practical decision, then choose the closest field pattern.

Closing Message

Purpose: End with the three principles: start practical, validate carefully, expand cleanly.

To summarize, our approach is to start practical, validate carefully, and expand cleanly.

We select the minimum useful scope for the current decision, confirm equipment and interfaces carefully, and then add zones, sensors, endpoints, and software functions over time.
